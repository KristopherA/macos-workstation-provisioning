User preferences (D15, R21)
Module 2 has two entry points and one shared per-entry pipeline.
UserSpace-preferences.txt runs as the target user in that user's own GUI session. It refuses root, the operator account workstationadmin, and a caller who is not the console user. The user must be listed in session policy USERS. The caller's HOME must equal the dscl NFSHomeDirectory record, or the script refuses with exit 4. A home folder path that contains a space is not handled: this path refuses with exit 4. Defaults go through the user's own cfprefsd. Backups go under the user's Library/Application Support/WorkstationProvisioning/backup, unique, mode 0700. The report writes backup= as ~/Library/Application Support/WorkstationProvisioning/backup/<dir>. The account name never appears. Expand that "~" form as the user's home only when restoring.
Apply on this path needs both USER_PREFS_CONSENT=yes in the trusted session policy and the typed word APPLY on a terminal. "Terminal" means stdin: the stock tty tool, read through wsp_run, must exit 0 and print a /dev/ name, and the word is read from stdin. The prompt is written to file descriptor 5, which is a copy of the caller's real stderr taken before the library sends file descriptor 2 to /dev/null. The prompt is therefore visible on the terminal. Piped or redirected stdin, EOF, an empty answer, or any other text is a refusal. That refusal is PENDING_CONSENT apply-gate. The run continues as inspect, writes nothing, and ends with exit 2 if nothing else fails. The library has no test-only confirmation branch. The APPLY question is asked last, and never when apply is already refused. UserSpace-preferences.txt does not accept --output. Report records go to stdout. Redirect stdout only when you capture a report. Leave the terminal stderr in place so the prompt stays visible.
A missing or non-yes consent key, an unreadable MDM enrollment state, or a not-macOS run still reports BLOCKED_POLICY apply-gate and drops to inspect without asking APPLY.
The launcher module userprefs is the offline path, through sudo like the other root modules. Use it only for a home that is not logged in and has no process owned by that user's UID. Targets are the session policy USERS, never workstationadmin. The offline path has no second APPLY prompt. It uses the launcher APPLY prompt plus USER_PREFS_CONSENT=yes.
The module refuses a user, before any preference read or write, when: the account is not proven to exist (UNKNOWN); UniqueID is unreadable (UNKNOWN); UniqueID is below 500 (BLOCKED_POLICY); the home directory record is not exactly /Users/<user>, including a home path with a space (UNKNOWN); the home, Library, or Library/Preferences is missing, a symlink, not owned by the target user, group/other writable, or has an ACL (BLOCKED_POLICY); or an existing preference file is a symlink, not a regular file, or not owned by the target user (BLOCKED_POLICY for the whole user). Login state is read fresh for each target user, just before the plist checks: who, the console user, and ps -axo uid=. Every process-list line must be a bare number, and at least one UID-0 process must be visible. If the user is the console user or appears in who, the result is BLOCKED_POLICY (logged in; use the UserSpace path). If a process is owned by the target UID, the result is BLOCKED_POLICY until that user has no process. Any reader fault, or a listing with no visible UID-0 process, is UNKNOWN. After those checks pass, the write identity is set. Right before the first write for that user, after the checked backup and the identity re-check, the login state is read once more (who, the console user, and the process list). A session or process found at that later read refuses the write. Later entries of the same user are not re-read, because an earlier write in this run may leave a process of that UID (Mac item 15). There is no launchctl proof of "no session" (Mac item 16). Those limits are accepted for this pilot. Pilot precondition (S9): turn Remote Login and Screen Sharing off for the target accounts, so no remote session of a target user can exist that who and the console user would miss.
The offline path does not create Library/Preferences. The write runs as the target user: sudo -n -u USER defaults write <home>/Library/Preferences/<domain> KEY -type VALUE. After a write, the file must be a regular file owned by that user and not group/other writable, or the check is FAILED. The written value is then also verified on disk with plutil -convert xml1 -o - as the target user, typed, leaving the file untouched. That read is retried at most three times, one second apart. Success on any read stops the loop. A value that never appears costs exactly three reads, then FAILED. The own-session path has no on-disk read. Offline backups use the root-owned backup area. backup= is the full absolute directory. OWNER.txt is written beside each backup copy as OWNER <user> MODE <mode|absent> FILE <name>, mode 0600. If that marker cannot be written, the backup directory is discarded and the write is refused. The own-session path does not write OWNER.txt.
The operator file is user-prefs.conf in the trusted session-policy directory, beside session.conf. It is root-owned and trust-checked like session.conf. There are no defaults. A missing or empty file, or one syntax error anywhere, rejects the whole file (BLOCKED_POLICY preferences-config). Nothing is applied. Grammar is one entry per line, id|domain|key|type|value. "#" comments and blank lines are allowed. At most 64 entries.
id is unique and must match ^[a-z0-9][a-z0-9-]{0,31}$. A 24-character or longer id with no hyphen is reported as [opaque-token] in non-path fields. Use hyphens in long ids.
domain is 1-100 characters of [A-Za-z0-9._-], first character alphanumeric, and must not contain "..".
key is 1-100 characters of [A-Za-z0-9._-], first character alphanumeric or underscore, and must not contain "..". The accepted regular expression is [A-Za-z0-9_][A-Za-z0-9._-]{0,99}, so a key may start with any number of underscores. A domain may not start with an underscore. The fixed key table still refuses an unlisted key.
type is bool, int, or string.
value: bool is true or false; int must match ^(0|-?[1-9][0-9]{0,8})$ (0 and negatives allowed, no leading zeros, no -0, no +); string must match ^[A-Za-z0-9._+][A-Za-z0-9._+-]{0,63}$ and must not start with "-".
A repeated id, or a repeated (domain,key) pair even with another type or value, rejects the whole file.
The allowlist is a fixed domain-to-key table in the library. It is a constant, not operator config. Configuration can only narrow it. There is no run-time way to add a domain or a key. No ByHost domains. The domains are NSGlobalDomain (stored as .GlobalPreferences), com.apple.dock, com.apple.finder, com.apple.AppleMultitouchTrackpad, com.apple.driver.AppleBluetoothMultitouch.trackpad, com.apple.desktopservices, and com.apple.menuextra.clock.
Exact keys, by domain:
NSGlobalDomain: AppleShowScrollBars, AppleShowAllExtensions, NSAutomaticSpellingCorrectionEnabled, NSAutomaticCapitalizationEnabled, NSAutomaticPeriodSubstitutionEnabled, NSAutomaticQuoteSubstitutionEnabled, NSAutomaticDashSubstitutionEnabled, com.apple.swipescrolldirection.
com.apple.dock: autohide, autohide-delay, autohide-time-modifier, tilesize, largesize, magnification, orientation, show-recents, minimize-to-application, mru-spaces, launchanim, show-process-indicators.
com.apple.finder: ShowPathbar, ShowStatusBar, AppleShowAllFiles, FXPreferredViewStyle, FXEnableExtensionChangeWarning, _FXShowPosixPathInTitle, FXDefaultSearchScope, NewWindowTarget.
Both trackpad domains: Clicking, TrackpadRightClick, TrackpadThreeFingerDrag, Dragging.
com.apple.desktopservices: DSDontWriteNetworkStores, DSDontWriteUSBStores.
com.apple.menuextra.clock: ShowDate, ShowDayOfWeek, Show24Hour, ShowAMPM, IsAnalog, FlashDateSeparators.
Deliberately not in the table: any other NSGlobalDomain key, including NSDocumentSaveNewDocumentsToCloud and AppleKeyboardUIMode; Dock hot corners (wvous-*) and *-immutable lock-ins; Finder FXRemoveOldTrashItems and WarnOnEmptyTrash.
A syntactically valid entry for another domain reports BLOCKED_POLICY "domain is not in the suite allowlist" for that entry. A key outside the table for an allowed domain reports BLOCKED_POLICY "key is not in the suite allowlist for this domain". Other entries continue.
Per entry, in this order, each ending the entry with no write: allowlist table; Managed Preferences files; management profiles; typed read; equal or inspect or apply as before.
Managed Preferences: a file, directory, or symlink named <plist>.plist under /Library/Managed Preferences or /Library/Managed Preferences/<user> reports BLOCKED_POLICY for that entry. If the folder or the per-user folder is a symlink, a plain file, or not readable, or the user name is invalid, the state is UNKNOWN. If the folder is absent, or is a real readable directory without that entry, the check continues.
Then management profiles (BLOCKED_POLICY when managed, including when the listing names this domain, NSGlobalDomain, com.apple.mcx, or ManagedClient; UNKNOWN when unreadable or not the empty-listing sentences plus enrollment No); typed read (UNKNOWN when unreadable; UNSUPPORTED when a stored value has another type or is outside the grammar, never overwritten); equal value ALREADY_CORRECT with evidence=stored-pref; inspect PROPOSED (verify converts a remaining difference to FAILED); apply takes one checked backup per plist and run, re-checks the source, writes, and reads back. Offline apply then does the on-disk plutil check described above. Success is CHANGED_VERIFIED for the stored value. A closing PENDING_LOGIN record asks for confirmation in System Settings. Exit codes are the same as elsewhere (0 complete, 2 incomplete, 3 FAILED, 4 refused, 64 usage).
Generic public-repo examples, not required values. These keys are in the table:
example-bool|com.apple.dock|autohide|bool|true
example-int|com.apple.dock|tilesize|int|48
example-str|NSGlobalDomain|AppleShowScrollBars|string|Always

First-login LaunchAgent (D14, module 3, R01/R02)
Purpose: apply the operator's user-prefs.conf once per listed user, at that user's first GUI login, without a typed word, and nothing else.
There are two parts and one narrow writer.

Installer: launcher module firstlogin, through sudo, as root. Default mode inspect classifies five targets and writes nothing.
Apply needs the launcher typed APPLY, the root apply gate, FIRSTLOGIN_CONSENT=yes in the root-owned policy, USER_PREFS_CONSENT=yes and USERS in the session policy, and a valid user-prefs.conf (the same loader as module 2). Any missing one reports BLOCKED_POLICY apply-gate, runs inspect only, and writes nothing.
FIRSTLOGIN_LABEL in policy.conf is a generic reverse-DNS label: 3 to 5 dotted parts of [a-z0-9-], first part starting with a letter, at most 100 characters, never com.apple.* or apple.*. The default is com.example.workstationprovisioning.firstlogin. If the FIRSTLOGIN_LABEL line is present and the policy reader rejects the value, or the returned value fails that grammar, the module reports BLOCKED_POLICY fl-label and classifies or writes nothing. Only an absent line uses the default. FIRSTLOGIN_USERS is removed from the root policy allowlist. A FIRSTLOGIN_USERS line is ignored like any unknown key. The installer binds to session policy USERS.
Apply installs five targets in this order, each with a checked backup (an ABSENT marker for a new file), a temporary file in the same folder, chmod, mv, and verification of content, owner, and mode:
1. /Library/Management/WorkstationProvisioning-Session/bin/  root, 0755, new folder.
2. /Library/Management/WorkstationProvisioning-Session/bin/workstationadmin-lib.txt  root, 0444, a copy of the suite library of this run.
3. /Library/Management/WorkstationProvisioning-Session/bin/UserSpace-preferences.txt  root, 0444, a copy of the suite file of this run.
4. /Library/LaunchAgents/<label>.plist  root, 0644, the exact plist text below.
5. /Library/Management/WorkstationProvisioning-Session/firstlogin-consent.conf  root, 0644, written last. This record arms the agent.
A target that is a symlink, a non-regular object, has an ACL, or is not owned by root refuses the whole install: BLOCKED_POLICY apply-gate, zero writes. A group or other-writable folder, or an untrusted session or LaunchAgents folder, also refuses the whole install.
An identical target is left alone (ALREADY_CORRECT, no backup). A failing step stops the install. Later steps are FAILED "not attempted". The consent record is never written after a failure (exit 3). The suite does not remove or roll back automatically. Use the manual runbook procedure.
The plist has exactly four keys and no other key: Label; ProgramArguments equal to /bin/bash, /Library/Management/WorkstationProvisioning-Session/bin/UserSpace-preferences.txt, --mode, apply, --firstlogin; RunAtLoad true; LimitLoadToSessionType Aqua. There is no KeepAlive, StartInterval, WatchPaths, UserName, environment, socket, or working directory. After a plist is present, the installer runs plutil -lint as a read-only check. The expected text is "<path>: OK".
The installer runs no launchctl command. It creates no LaunchDaemon, no login hook, and no TCC change. It uses no network. It changes no account or group. It never writes into any user's home folder.
The consent record is exactly three lines:
FIRSTLOGIN_CONSENT_RECORD=1
PREFS_SHA256=<64 hex of the current user-prefs.conf>
USERS=<the exact session USERS value>
If user-prefs.conf or USERS later changes, inspect reports PENDING_CONSENT fl-consent-stale. The agent writes nothing until the operator runs the installer in apply mode again, with a new typed APPLY. The old record is kept in the backup. The decision is repeated, never inherited.

Agent: UserSpace-preferences.txt --mode apply --firstlogin, started by launchd from the installed copy only, as the logging-in user, or later run by that user from a Terminal.
A copy from another folder is refused (exit 4). --firstlogin without --mode apply is usage (exit 64). Root is refused. An account not listed in USERS is refused. A HOME that does not match the directory record is refused.
First action: if ~/Library/Application Support/WorkstationProvisioning/firstlogin.done exists as a regular file owned by the user, the process exits 0 with no output and no write. That is every later login. A done marker that is a symlink, another kind of object, or owned by another account, or a report folder that is a symlink, is refused (exit 4). A bad marker is never treated as absent.
Otherwise the module-2 pipeline runs, and two gates both apply: the consent record, and this script's own typed word APPLY, asked after the list is loaded and the record is valid. That prompt is not the launcher APPLY prompt. The record must be a regular file, root-owned, not group or other writable, without an ACL, and equal to the text built from the current user-prefs.conf hash and USERS. Missing, bad, stale, unknown, or unreadable reports PENDING_CONSENT apply-gate, runs inspect only, writes nothing, writes no marker, and ends with exit 2 if nothing else fails. A bad record is also PENDING_CONSENT in this draft.
At a login started by launchd there is no terminal. The agent then reports PENDING_CONSENT firstlogin-typed-APPLY, writes nothing, takes no backup, writes no marker, and ends with exit 2 if nothing else fails. There is no automatic apply.
The notification shows for each first-login run that stops at PENDING_CONSENT. A run without --firstlogin does not show a notification.
A first-login run stops at PENDING_CONSENT when the consent record is missing, bad, stale, unknown, or unreadable, or when no typed APPLY is given. That includes a login started by launchd and a Terminal hand-run of --firstlogin. These are product UI strings, not STE text. The title is exactly:
Workstation setup
The text is exactly:
Workstation setup is waiting for approval. Nothing was changed.
The text is fixed. It contains no asset tag, user name, key, or policy data. The notification is report-only. It writes no file and does not change the outcome. The PENDING_CONSENT record stays, and its detail ends with notify=shown (none) or notify=failed (not-found|other|timeout). not-found means the notification tool was not found. other covers no GUI session and tool errors. timeout means the tool was stopped after about 10 seconds. A failed notification changes nothing else: still PENDING_CONSENT, zero writes, no marker, exit 2.
The notification is not shown when a first-login apply proceeds, or by any root module. The firstlogin installer script does not call the notification tool. Only a --firstlogin run, through the library helper, may call it at PENDING_CONSENT.
The user, or the operator as that user, must open Terminal, run the installed copy, and type APPLY:
/bin/bash /Library/Management/WorkstationProvisioning-Session/bin/UserSpace-preferences.txt --mode apply --firstlogin
After a first-login apply that still remains in apply mode and that has no FAILED record, a marker of the exact form DONE rc=<0|2> run=<id> is written at ~/Library/Application Support/WorkstationProvisioning/firstlogin.done, mode 0600, through a temporary file and mv, with the folder mode 0700. rc=2 covers an incomplete run, including the closing PENDING_LOGIN note. If any step is FAILED, no marker is written, and the next run tries again. If the marker cannot be written, the check is FAILED and the next run tries again.
In first-login mode, including that Terminal hand-run, backups use one reused folder, ~/Library/Application Support/WorkstationProvisioning/backup/firstlogin-original, mode 0700. The first try records the original plist, or a <name>.ABSENT marker. Later tries reuse that folder and never overwrite those originals, so retries do not grow the backup set. The ordinary own-session path, without --firstlogin, still uses one unique backup folder per run.
UserSpace-preferences.txt does not accept --output. Report records go to stdout. At login, launchd typically gives /dev/null for stdin, stdout, and stderr, so the PENDING_CONSENT record may not be kept. Do not assume a saved report exists in the user's folder.
A listed user may create firstlogin.done in their own folder and so skip their own first-login run. That residual is stated, not hidden. launchd behaviour is not validated.

Removal and rollback are manual. The suite removes nothing. As root, and only after the user's session is closed, do this in order:
1. Delete firstlogin-consent.conf. The agent then reports PENDING_CONSENT at any further login.
2. Delete /Library/LaunchAgents/<label>.plist.
3. Delete the two installed copies and the bin folder.
4. For a user who already logged in: restore each preference from that user's backup folder ~/Library/Application Support/WorkstationProvisioning/backup/<dir>. An ABSENT marker means delete the live file again. Remove firstlogin.done so a later run may occur.
Install backups of replaced files are under the root backup area /Library/Management/WorkstationProvisioning/backup/.
Never: launchctl bootstrap or kickstart from root into a user session, a login hook, a LaunchDaemon, a TCC change, network use, an unlisted user, a list other than the operator's user-prefs.conf, a key outside the fixed table, or a typed secret.

Shared-resource copy (D15, module 4, R10)
The launcher module shared is restored in this draft, narrowly. It runs through sudo, as root. Destination is /Users/Shared/<item>.
Apply needs the launcher typed APPLY, the root apply gate, and SHARED_COPY_CONSENT=yes in the root-owned policy. Without that consent key the module stays inspect-only, reports PROPOSED or ALREADY_CORRECT, and writes nothing.
Root-policy keys, with no site value in the suite:
SHARED_SOURCE_DIR: an absolute path chosen by the operator. Allowed characters are A-Za-z0-9, space, period, underscore, plus, hyphen, and slash. The value must not contain "..", must not contain "//", must not have a trailing slash, and must not be an ancestor of /Users/Shared.
SHARED_ITEMS: names separated by ":", at most 50, no "/", no leading ".", no duplicate.
SHARED_COPY_CONSENT: must be yes for apply.
SHARED_CONFLICT: skip (the default) or backup-replace. Any other value refuses apply.
These keys are read from policy.conf. SHARED_ITEMS is also still allowlisted in the session reader. UserSpace-audit reads only the session value, as a read-only presence check. The module-4 writer reads only the root-policy value. The session value never changes what is copied. Keep both lists equal.
Every source entry must be a regular file or a real folder owned by root or the operator, not group or other writable, with no setuid, setgid, or sticky bit, with no ACL, and with a safe name. Caps are 500 entries, depth 8, 64 MiB per file, and 256 MiB per item. One unsafe or missing item refuses the whole apply (zero writes). If the source folder is absent, the result is PENDING_CONSENT.
Each item is re-checked, copied with cp -R -P into a root-only staging folder, compared, given explicit modes 0755 for folders and 0644 for files, given owner root:wheel, compared again, and only then renamed into /Users/Shared, never over an existing item. The result is compared once more. Results are never links.
With SHARED_CONFLICT=skip, a differing destination item is never touched (BLOCKED_POLICY). With backup-replace, the existing item is first moved whole into a unique backup folder under the policy backup area, that move is verified, and then the new copy is put in place. A failure on a replaced item is restored. If putting the replaced item back fails and its undo also fails, the report says: "putting the replaced item back failed and its undo failed: a partial root-only folder may remain at the name, the rest stays in the backup". If a folder placement fails and its undo also fails, the report says: "the placement failed and its undo failed; a partial root-only folder may remain at the name". In that case, inspect that root-owned folder and remove it by hand only after you check it. A failed step stops the module. Later items are FAILED "not attempted". The staging folder is removed. The suite does not otherwise remove destination items.
Finder aliases, URL aliases, and Finder locks remain manual (PENDING_LOGIN).
Placement uses an atomic no-clobber claim of the destination name (library helper wsp_rename_nofollow: link for a file, mkdir for a folder, then the folder entries are renamed with mv -h on macOS). If anything appears at that name after the last check, a symlink, a dangling symlink, a file, or a folder, it is never followed or replaced. The item is FAILED, with the text "something appeared at the destination right before the rename; refused, nothing placed or written behind it". The raced entry is left as it is. Staging and /Users/Shared must be on the same volume. There is no copy fallback if they are not.
S-4: every copied file is published 0644, including a source file that others cannot read, for example mode 0600. The source folder must never hold secrets. The suite source files in this archive also ship at mode 0644.
Residual: /Users/Shared is world-writable and sticky. A raced name is refused by the no-clobber claim, not overwritten. This writer is not validated on a Mac.

App install (D16, module 5, R11/R12)
The launcher module apps is restored in this draft, narrowly. It runs through sudo, as root.
It installs only from a local vendor .pkg or .dmg that the operator places in a folder. The suite never downloads, never uses the App Store, never uses an Apple Account, and never makes a purchase. APP_LIST entries with /store stay manual (PENDING_CONSENT). Sign-in, licensing, first launch, and app privacy consent stay with the user.
Apply needs the launcher typed APPLY, the root apply gate, APP_INSTALL_CONSENT=yes in the root-owned policy, a valid APP_TEAM_IDS allowlist, valid APP_PACKAGES and APP_SOURCE_DIR, trusted folders, and this module's own typed APPLY. Without those gates the module stays inspect-only and writes nothing.
Root-policy keys, with no site value in the suite:
APP_PACKAGES: Label=FILE entries separated by ":". Label must be a non-store APP_LIST label, exact, with spaces allowed, and at most one entry per label. FILE is a plain name of A-Za-z0-9, space, period, underscore, plus, or hyphen, ending in .pkg or .dmg, with no "/", no leading "." or "-", no trailing space, and at most 100 characters. Example: ExampleChat=ExampleChat-1.0.pkg:ExampleNotes=ExampleNotes 2.dmg.
APP_TEAM_IDS: Label=TEAMID entries separated by ":" only. No commas, no spaces around the separator, and no bare Team IDs. TEAMID is exactly 10 characters from A-Z and 0-9. No duplicate label. Example: ExampleChat=ABCDE12345:ExampleNotes=FGHIJ67890. Those example Team IDs are fictional. The Team ID is bound to its own label: a package signed by another listed Team ID is still refused.
APP_SOURCE_DIR: an absolute folder. Allowed characters are A-Za-z0-9, space, period, underscore, plus, hyphen, and slash. The value must not contain "..", must not contain "//", must not have a trailing slash, must not use a "." or ".." path segment, must be at most 200 characters, and must not be under /Applications, /Library/Management, or /System. The folder and every ancestor must be trusted (canonical path).
APP_INSTALL_CONSENT: must be yes for apply.
APP_TEAM_IDS unset or empty is BLOCKED_POLICY (apply-gate and install-config). That check is first. A package whose label has no APP_TEAM_IDS entry is BLOCKED_POLICY. APP_PACKAGES unset or malformed, APP_LIST unset or malformed, APP_SOURCE_DIR unset or invalid, or APP_INSTALL_CONSENT not yes, also refuses apply.
The package file must be a regular file, not a symlink, owned by root or the operator, not group or other writable, with no setuid, setgid, or sticky bit, with no ACL, and with size from 1 byte through 4 GiB.
A .pkg must pass pkgutil --check-signature with exit 0 and exactly one line "Status: signed by a developer certificate issued by Apple for distribution", exactly one "Notarization: trusted by the Apple notary service", exactly one leaf "1. Developer ID Installer: <name> (<TEAMID>)", and one "<n>. Apple Root CA" line. The Team ID must equal the label's APP_TEAM_IDS value. Then spctl -a -t install must exit 0.
A .dmg must pass codesign --verify --strict with this requirement, and spctl -a -t open --context context:primary-signature must exit 0. The requirement is: anchor apple generic and certificate 1[field.1.2.840.113635.100.6.2.6] exists and certificate leaf[field.1.2.840.113635.100.6.1.13] exists and certificate leaf[subject.OU] = "<TEAMID>". An unsigned disk image is refused (BLOCKED_POLICY). Ask the vendor for a .pkg or a signed .dmg.
The app must be a real folder, not a symlink. It must pass codesign --verify --deep --strict with the same requirement, and spctl -a -t exec must exit 0.
Any configured package that fails a pre-check refuses the whole apply, with zero writes. A failure during the install is partial: apps installed earlier in the same run stay, the failing vendor package may leave a partial install, later packages are not attempted, and the run ends FAILED, exit 3. After a FAILED run, inspect /Applications. The suite does not uninstall.
An app already present at /Applications/<BundleName>.app is never replaced. If it passes the app checks, the result is ALREADY_CORRECT. Otherwise it is BLOCKED_POLICY. Remove or update it by hand. A symlink at that name is BLOCKED_POLICY. A second apply that finds the apps present and verified is ALREADY_CORRECT, with no question and zero writes.
/Applications must be a real folder, owned by root, with no ACL, and mode 0755, or 0775 with group admin. The policy folder used for staging must be trusted.
The module asks its own typed word APPLY on /dev/tty after the checks, listing each app and its Team ID: "Install N app(s) from verified local packages: <Label> (Team ID X); ...". The exact word APPLY is required. This is in addition to the launcher APPLY prompt. When the module is started directly with sudo, only this module prompt is asked. The prompt is asked only if at least one package is to be installed. No terminal, EOF, or another answer reports PENDING_CONSENT apply-gate and writes nothing.
Apply order, after the gates: re-check the source file; copy it with cp -P into a root-only staging folder under the policy folder, name .apps-stage.XXXXXX, mode 0700; compare; chmod 600; verify the staged copy again.
A .pkg is installed with installer -pkg <staged copy> -target /. The vendor package's own scripts run as root. The Team ID allowlist is that trust decision. A non-zero installer exit is FAILED. The suite does not uninstall a partial vendor install.
A .dmg is attached with hdiutil attach -nobrowse -readonly -noautoopen -mountpoint <private folder in the staging folder>. The app at <mount>/<BundleName>.app must pass the app checks. ditto copies it into the staging folder. The image is detached (hdiutil detach, then once detach -force). Then chown -R -h root:wheel and chmod -R go-w. The staged app is checked again. Placement uses wsp_rename_nofollow (no-clobber, never through a link). If a folder placement fails and its undo also fails, a partial root-only folder may remain at the app name. Inspect that folder and remove it by hand only after you check it.
An EXIT trap, and INT, TERM, or HUP ending with exit 3, detaches a still-attached image. The EXIT trap also probes a mount point that cannot be removed, so a signal during attach does not leave the image attached. If an image cannot be detached, the record says so and the staging folder is kept. Otherwise the staging folder is removed.
Both package types: the installed /Applications/<BundleName>.app must pass the app checks, else FAILED "installed, but the app fails verification", and it is not removed automatically.
Report records include install-config, install-source, install-<Label> (spaces in the label become "-"), and apply-gate. The inspect records app-<Label>, default-browser, and app-privacy-consent still run after the install step. The absent text for a non-store app now says to supply the vendor package in APP_SOURCE_DIR and APP_PACKAGES.
Never: quarantine removal, spctl rule changes, --noqtn, sudo inside the module, App Store tools, TCC edits, or downloads.

FileVault enable and NEW-key file (D17, module 6, R18/R19, the key-file decision)
The launcher module filevault is restored in this draft, narrowly. It runs through sudo, as root.
When FileVault is off, FILEVAULT_CONSENT=yes, FILEVAULT_KEY_DIR is a valid local folder, the asset tag is recorded, and the operator types APPLY, this module enables FileVault and writes the NEW personal recovery key to <asset-tag>-FileVault-recovery-key.txt in that folder. The operator types the account password into fdesetup, not into this suite. The key is never shown by the suite.
The module never disables FileVault, never rotates a key, never reads an existing key or key file, and never writes a key except into that new file in this run.
Apply needs the launcher typed APPLY, the root apply gate, FILEVAULT_CONSENT=yes in the root-owned policy, a valid FILEVAULT_KEY_DIR, a valid recorded asset tag, FileVault reported exactly off, and this module's own typed APPLY. Without those gates the module does not enable FileVault and does not write a key file.
Root-policy keys, with no site value in the suite:
FILEVAULT_CONSENT: must be exactly yes for the scripted enable and key file. Any other value, when the other key is also set, reports BLOCKED_POLICY and does not enable FileVault.
FILEVAULT_KEY_DIR: the operator-chosen folder. The value must be absolute. Allowed characters are A-Za-z0-9, space, period, underscore, plus, hyphen, and slash. The value must not contain "//", must not use a "." or ".." path segment, must not have a trailing slash, and must be at most 200 characters. It must not be under /Applications, /Library/Management, /System, /private, /tmp, /var, /usr, /bin, or /sbin, must not be the suite folder or a folder under it, and must not be a cloud-sync folder. Interface section 13e lists the refused cloud-sync name fragments. The folder must already exist, must not be a symlink, and must be on a local disk (df -l, with a line that starts with /dev/). A local external disk is allowed. A network share is refused. The folder and every ancestor must be trusted (the canonical path equals the given path, so no symlink is in the path; the owner is root or the operator; the folder is not group-writable or other-writable and is not sticky; there is no ACL). Prefer a folder on the approved external storage so the key never lands on the internal disk.
Both FILEVAULT_KEY_DIR and FILEVAULT_CONSENT unset, and FileVault off: PENDING_CONSENT key-export "not configured". Enable FileVault in Settings and save the NEW key by hand, as in the earlier manual path. If only one of those keys is set, or FILEVAULT_CONSENT is not exactly yes, or the folder, tag, or name check fails, the result is BLOCKED_POLICY, and FileVault is not enabled.
The key file name is <asset-tag>-FileVault-recovery-key.txt in FILEVAULT_KEY_DIR. The asset tag is the root-only asset-tag record, already validated: 1-24 letters, digits, or hyphens, with no leading or trailing hyphen. Content is the key and one newline. Mode is 600 from the first moment of creation. The owner is the operator (chown -h after the create). The owner confirmed that choice on 18 November 2026 at 21:31 local time. Root-only ownership is not adopted. Anything already at that name, including a file, a symlink, or a dangling symlink, is refused and is never overwritten.
When: only when this run turns FileVault on. FileVault already on or encrypting: PENDING_CONSENT key-export "FileVault is already on: no key exported". No enable, no rotation, no re-enable, and nothing is read. The existing key file is left untouched. Unknown FileVault state: UNKNOWN, nothing is enabled, and no key is exported.
Order:
1. Read-only pre-checks on inspect and apply: FileVault is exactly off, FILEVAULT_CONSENT=yes, the asset tag, the folder grammar, the folder exists and is not a symlink, the folder is trusted, nothing is at the key file name, and the folder is on a local disk. A refusal is BLOCKED_POLICY key-export, and FileVault is not enabled. Inspect after a successful pre-check is PROPOSED.
2. The root apply gate, then the module typed APPLY on the terminal. The module prompt asks to enable FileVault now and write the NEW key to the asset-tag key file in FILEVAULT_KEY_DIR, mode 600, and says that fdesetup will ask for the operator password. The exact word APPLY is required. This is in addition to the launcher APPLY prompt. No terminal, EOF, or another answer reports PENDING_CONSENT apply-gate and changes nothing.
3. The state and the pre-checks run again. If FileVault is no longer off, the result is BLOCKED_POLICY, and nothing is enabled.
4. Before the enable: the empty key file is created exclusively (umask 077 and noclobber), held open on file descriptor 7, given to the operator, and verified as a regular non-link empty file, mode 600, owner the operator. Any failure at this step removes the file this run made, reports FAILED key-export "refused before the enable", and does not enable FileVault, exit 3.
5. INT, TERM, and HUP are ignored from the enable until the key is on disk. Those ignored signals are inherited by fdesetup, so Control-C at the password prompt does not cancel the enable. The command is fdesetup enable -user <operator> -outputplist, with the terminal as stdin. The operator types the password into fdesetup. Standard output is captured in memory only. The key is taken with shell matching only: exactly one RecoveryKey field followed by a string of six groups of four characters from A-Z and 0-9, separated by hyphens. The printf builtin writes the key and a newline to file descriptor 7. The key never appears in argv, the environment, standard output, standard error, a report, a log, or a temporary file. Reports print a key-shaped value as [secret-shape].
6. The size is verified (key length plus one). Success is CHANGED_VERIFIED for key-export and, when the later status is On or in progress, for fv-enable. A restart can be required on some Macs.
If the enable fails and FileVault is still exactly off: FAILED fv-enable, the empty file is removed, exit 3, and nothing is lost.
If any failure after the enable may have succeeded (a non-zero exit while FileVault is not off, no single valid key in the output, or a write or size failure): the incomplete file is removed, FAILED key-export, exit 3, and the report guidance is: "FileVault is on, but its NEW recovery key was NOT saved (it is never shown). Do not restart. Create a new personal key by hand (fdesetup changerecovery -personal) and save it; see runbook". The key is never printed.
The EXIT trap removes the file this run made if the key is not yet on disk.
Residual, documented and not fixable in this shell: a SIGKILL or a power loss between the enable and the write; a FIFO or device planted at the name by root or the operator between the last check and the open (the post-open checks then refuse it, and nothing is written into it). After a crash, SIGKILL, or power loss, check fdesetup status and the key file. An empty leftover file makes the next run BLOCKED_POLICY, because something already exists at the name. The operator removes that leftover file only after checking it. If FileVault is on and no key was saved, do not restart. Create a new personal key by hand with fdesetup changerecovery -personal and save it.
key-external-import remains PENDING_CONSENT: the operator copies the key file to the approved external storage. That copy is manual and is not verified by code. Prefer to keep no copy on the internal disk after the external copy is made.
restart-unlock-test remains PENDING_LOGIN and is manual.
Never: an Apple Account, an institutional key, escrow, deferred enablement options, authenticated restart, a TCC change, or a paid action. Never put a key, a filename with an asset tag, or a destination path in a shareable report, in chat, in logs, or in these documents.

5. Exit and check semantics
0 = completed evaluated checks. Help and nonlisted-user no-ops also return 0.
2 = incomplete with no FAILED check. 3 = failed check or detected report write failure.
4 = safety refusal. 64 = argument usage error.
Launcher can map a module's unexpected exit to 4. Read the records, not only exit status.
A selected-subset exit 0 cannot certify acceptance of all R01-R42.
Statuses are ALREADY_CORRECT, CHANGED_VERIFIED, PENDING_LOGIN, PENDING_CONSENT,
UNSUPPORTED, FAILED, BLOCKED_POLICY, PROPOSED, and UNKNOWN.
Only the first two complete an evaluated check.
MANUAL is not a code status. Manual evidence uses pending status and evidence=manual.
UNKNOWN means an observation was unavailable, not proof of violation or compliance.
Account existence reports "missing" (no) only when dscl exits 56, stdout is empty, the stderr class is not-found, and capture succeeds.
The not-found class covers eDSRecordNotFound and "No such key". Confirm both texts on a Mac.
Anything else is UNKNOWN. UNKNOWN is incomplete evidence, never a pass, and never FAILED for indeterminate existence.
The accounts module maps confirmed absence to PENDING_CONSENT for guided creation.
Preflight and audit map a missing required operator record to FAILED R03 operator-record.
Stored preference matches remain PENDING_LOGIN with evidence=stored-pref.
Manual records cannot be ingested or turn pending code results into PASS.

6. Exact diagnostics and links
Schema is wsp-report/1. Records begin WSPREC with TAB-separated key=value fields.
A check record may carry an optional trailing backup=<path> field.
That field uses grammar class path: at most 200 characters of [A-Za-z0-9._ /-], with no ".." or "//", either an absolute path starting with "/" or the one accepted ~/Library/Application Support/WorkstationProvisioning/backup/<dir> form.
It is the one field class that skips the long-opaque-token test. All other classes still apply, including home-path redaction.
On the updates writer and the offline userprefs path, backup= is the full absolute backup directory. A user name inside that path is redacted as usual.
On the UserSpace-preferences path, backup= is exactly ~/Library/Application Support/WorkstationProvisioning/backup/<dir>. The home folder is replaced by "~" so the account name never appears. Do not prepend a home folder to a root-style /Library/... value. Expand that "~" form as the user's home only when restoring.
The path class accepts an absolute path, or that one literal "~/..." prefix. Anything else starting with "~" is not accepted as a path. The path class skips the long-opaque-token test. All other classes still apply, including home-path redaction.
Common fields are schema and run. Run IDs use date/time, numeric zone offset,
and random suffix. They do not encode a machine identity.
Header fields are suite=0.18-d18-draft5, script, sha256, lib_sha256, suite_id, tz, os,
build, arch, report, plan_run, apply_run, and evidence_mode.
policy_id is in module-start, not the header, as the interface states.
module-start includes module, sha256, lib_sha256, suite_id, policy_id, os, build,
arch, report, mode, and euid. policy_id can be not-readable.
suite_id hashes the filenames/hashes of matching script files in the suite directory.
It is not the tar archive hash. Keep the immutable archive hash separately.
policy_id hashes readable private policy, not the readable session policy.
It does not identify accounts.list, asset-tag, or all runtime decisions.
Keep an approved nonsecret policy revision in the operator run record too.

Any run of 24 or more letters, digits, plus, slash, equals, or underscore in a non-path field is replaced as [opaque-token].
The path class is exempt. Use hyphens in long user-prefs.conf ids so a 24-character id does not become [opaque-token] in the check name.
Check fields are module, req, check, status, expected, observed, evidence, exit,
errclass, and detail. Evidence values are record, stored-pref, effective-cli,
session-ui, static, mock, manual, and none.
Error classes are none, permission, not-found, privacy-consent,
unsupported-option, timeout, parse, and other. No production/operator command timeout wrapper was found. Harness deadlines are separate.
Other record types include module-start, module-end, refused, module-refused,
run-end, and link. Audit/target script finish at module-end, not launcher run-end.
Launcher link flags populate header plan_run/apply_run and also emit type=link.
Audit link flags populate header fields. Links never approve evidence or skip work.
Launcher link grammar permits 1-48 letters/digits/plus/hyphens.
Audit also accepts letters/digits/plus/hyphens but has no equivalent parser length check.
Do not supply secret or identifying text in any link field.

The filter classifies raw values before grammar validation and uses whole-value markers.
Observation fields permit 64 characters; fixed-detail fields permit 200.
Overlength/unrecognized values become markers rather than truncated values.
After library load, raw tool stderr goes to /dev/null unless a command deliberately
captures its nonsecret status in memory. Fixed suite messages use original stderr fd 5.
The command wrapper classifies stderr in memory for errclass; it does not persist raw text.
Its capture integrity/NUL checks cover routed stdout, not every direct read. See section 10.
Account pseudonyms use a random run salt passed to modules through stdin.
They are not stable cross-run account IDs. Compare check family and protected local mapping.
D15 clears inherited WSP_* names before trust reads/parsing, except the validated fixture hook. It also discards inherited functions and unsets BASH_ENV before the first tool name is resolved.
The former salt-hygiene finding has a static repair. See section 10 for pilot limits.
Filtering remains best effort. Manually inspect/redact every proposed attachment.
No automatic upload or telemetry exists.
