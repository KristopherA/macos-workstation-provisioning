How to apply user preferences on a disposable Mac, logged-in path
Use UserSpace-preferences.txt. Run it as the target user in that user's own GUI console session.
Do not run it as root, through sudo, or as workstationadmin. The script refuses those callers and a caller who is not the console user.
The user must be listed in session policy USERS. HOME must equal the dscl NFSHomeDirectory record.
A home folder path that contains a space is not handled by module 2. This path refuses with exit 4.
Inspect is the default. Apply needs --mode apply, USER_PREFS_CONSENT=yes in the trusted session policy, and the typed word APPLY on a terminal.
"Terminal" means stdin: the stock tty tool must exit 0 and print a /dev/ name, and the word is read from stdin. The prompt is written to file descriptor 5, a copy of the caller's real stderr taken before file descriptor 2 is sent to /dev/null.
UserSpace-preferences.txt does not accept --output. Report records go to stdout. Redirect stdout only. Leave the terminal stderr in place so the prompt stays visible.
Piped or redirected stdin is a refusal. No terminal, an empty answer, or any other text reports PENDING_CONSENT apply-gate, continues as inspect, writes nothing, and ends with exit 2 if nothing else fails.
A missing or non-yes consent key, or an unreadable MDM enrollment state, reports BLOCKED_POLICY apply-gate and does not ask APPLY.
Use the baseline, apply, and post-audit loop on a disposable Mac. Do not skip the baseline.

1. Obtain explicit authorization for the disposable test Mac and the selected preference entries.
2. Place user-prefs.conf in the trusted session-policy directory, beside session.conf. The file must be root-owned and trust-checked. There are no defaults.
   Use the grammar id|domain|key|type|value. One syntax error, a missing or empty file, a repeated id, or a repeated (domain,key) pair rejects the whole file. Nothing is applied.
   Integers must be canonical: 0 or an optional minus and 1-9 digits with no leading zeros, no -0, and no plus.
   Limit the file to 64 entries. Use only keys that appear in the library domain-to-key table. Configuration can only narrow that table.
   Use hyphens in long ids. A run of 24 or more letters or digits in a non-path report field is shown as [opaque-token].
3. Set USER_PREFS_CONSENT=yes in trusted session.conf. Any other value, or an unset key, refuses apply and runs inspect only, without asking APPLY.
4. Arrange the target user's real GUI console session with a real terminal on stdin. Keep that user nonroot.
5. Run the target baseline audit first, then inspect preferences, each with a new output file.
   The audit accepts --output. UserSpace-preferences.txt does not. Redirect its stdout only.

/bin/bash "$SUITE/UserSpace-audit.txt" --output "$REPORT_DIR/target-baseline-prefs-d15-01.txt"

/bin/bash "$SUITE/UserSpace-preferences.txt" --mode inspect > "$REPORT_DIR/userspace-prefs-inspect-d15-01.txt"

7. If management state is BLOCKED_POLICY or UNKNOWN, stop. Do not override a managed payload or an unreadable enrollment.

/bin/bash "$SUITE/UserSpace-preferences.txt" --mode apply > "$REPORT_DIR/userspace-prefs-apply-d15-01.txt"

Use the backup directory from the written-key record's backup= field, not only the last path component in the detail.
The directory mode is 0700. Use the directory from the same run. Do not restore automatically and do not restart a daemon.

For an offline userprefs or updates backup, backup= is already the full absolute directory. Run the copy as root.

What happens at a listed user's first GUI login
The installed LaunchAgent starts /bin/bash /Library/Management/WorkstationProvisioning-Session/bin/UserSpace-preferences.txt --mode apply --firstlogin as that user. A copy from another folder is refused (exit 4).
If ~/Library/Application Support/WorkstationProvisioning/firstlogin.done already exists as a regular file owned by that user, the process exits 0 with no output and no write. Remove that file only when a new authorized run is required.
If the marker is a symlink, another kind of object, or owned by another account, the process refuses (exit 4). A bad marker is never treated as absent.
The first-login apply needs a valid consent record and its own typed word APPLY on a terminal, asked after the list is loaded. That prompt is not the launcher APPLY prompt.
At login there is no terminal. The agent reports PENDING_CONSENT firstlogin-typed-APPLY, writes nothing, takes no backup, writes no marker, and ends with exit 2 if nothing else fails. There is no automatic apply.
The notification shows for each first-login run that stops at PENDING_CONSENT. A run without --firstlogin does not show a notification.
These are product UI strings, not STE text. The title is exactly:
Workstation setup
The text is exactly:
Workstation setup is waiting for approval. Nothing was changed.
The text is fixed. It contains no asset tag, user name, key, or policy data. A failed notification changes nothing else. The PENDING_CONSENT record stays, and its detail ends with notify=shown (none) or notify=failed (not-found|other|timeout).
After that login, the user, or the operator as that user, opens Terminal and runs the installed copy, then types APPLY:

/bin/bash /Library/Management/WorkstationProvisioning-Session/bin/UserSpace-preferences.txt --mode apply --firstlogin

Redirect stdout only if you capture a report. Leave the terminal stderr in place so the prompt stays visible. Do not run a copy from another folder.
If the consent record is missing, bad, stale, unknown, or unreadable, or if no typed APPLY is given, that --firstlogin hand-run also reports PENDING_CONSENT, writes nothing, and writes no marker. The notification shows for that run as well. Run the firstlogin installer in apply mode again before retrying if the consent record is not valid.
After a hand-run with no FAILED record, the script writes firstlogin.done with the line DONE rc=<0|2> run=<id>, mode 0600. If any step is FAILED, no marker is written, and the next run tries again. Backups use the one reused folder ~/Library/Application Support/WorkstationProvisioning/backup/firstlogin-original. Later tries do not overwrite the original plists stored there.
The script does not accept --output. At login, report records go to stdout, which launchd may send to /dev/null. Do not assume a saved report exists in the user's folder.
A user can create firstlogin.done themselves and skip their own first-login run.
Confirm visible behaviour in System Settings after a successful hand-run. Keep PENDING_LOGIN pending until that confirmation. UNKNOWN and MANUAL evidence are never a pass.


How to retry a first-login run
1. If a previous hand-run reported FAILED, no firstlogin.done marker was written. After you inspect current state and obtain a new authorization, run the installed script in Terminal again and type APPLY. The reused backup folder firstlogin-original keeps the original plists and is not overwritten.
2. If firstlogin.done is present as a regular file owned by the user, and a new authorized run is required, delete only that file. Do not delete a symlink or an unexpected object until it is reviewed.
3. If the consent record is stale (user-prefs.conf or USERS changed), run the firstlogin installer in apply mode again, with a new typed APPLY, before the hand-run. The agent writes nothing while the record is stale.
4. Do not rerun a failed mutation blindly. Review the current state first.


How to remove the first-login LaunchAgent by hand
The suite removes nothing and does not roll back automatically. Do this as root, in this order, and only after the user's session is closed.

1. Delete /Library/Management/WorkstationProvisioning-Session/firstlogin-consent.conf. The agent then reports PENDING_CONSENT at any further login.
2. Delete /Library/LaunchAgents/<label>.plist, where <label> is FIRSTLOGIN_LABEL or the default com.example.workstationprovisioning.firstlogin.
3. Delete the two installed copies and the bin folder under /Library/Management/WorkstationProvisioning-Session/bin/.
4. For a user who already logged in: restore each preference from that user's backup folder ~/Library/Application Support/WorkstationProvisioning/backup/<dir>, as in the restore procedure above. An ABSENT marker means delete the live file again. Then delete firstlogin.done.
Install backups of replaced installer files are under /Library/Management/WorkstationProvisioning/backup/. Use the backup= field from the install report.

How to copy shared resources on a disposable Mac
Use the launcher module shared. Run it as workstationadmin in that account's own GUI console session, through the launcher.
Destination is /Users/Shared/<item>. Apply needs the launcher APPLY prompt, the root apply gate, and SHARED_COPY_CONSENT=yes in trusted policy.conf.

Example: ExampleChat=ExampleChat-1.0.pkg:ExampleNotes=ExampleNotes 2.dmg.
APP_TEAM_IDS uses Label=TEAMID entries separated by ":" only. No commas, no spaces around the separator, and no bare Team IDs. TEAMID is exactly 10 characters from A-Z and 0-9. APP_INSTALL_CONSENT must be yes.
APP_TEAM_IDS unset or empty refuses apply (BLOCKED_POLICY). That check is first. A package whose label has no APP_TEAM_IDS entry is refused. The package file must be a regular file, not a symlink, owned by root or the operator, not group or other writable, with no setuid, setgid, or sticky bit, with no ACL, and no larger than 4 GiB.
A .pkg must pass pkgutil --check-signature and spctl -a -t install, with a notarized Developer ID Installer signature and the allowed Team ID. A .dmg must pass codesign --verify --strict with the requirement that includes the Apple anchor, the Developer ID CA OID 1.2.840.113635.100.6.2.6, the Developer ID Application leaf OID 1.2.840.113635.100.6.1.13, and the Team ID, and must pass spctl -a -t open --context context:primary-signature. The app inside must pass codesign --verify --deep --strict with the same requirement and spctl -a -t exec. An unsigned disk image is refused. Ask the vendor for a .pkg or a signed .dmg.
A .pkg runs the vendor's own installer scripts as root. The Team ID allowlist is that trust decision.
Any configured package that fails a pre-check refuses the whole apply, and nothing is written. A failure during the install is partial: earlier apps stay, later packages are not attempted, and the run ends FAILED, exit 3. After a FAILED run, inspect /Applications. The suite does not uninstall a partial install.
An app already at /Applications/<BundleName>.app is never replaced. If it verifies, the result is ALREADY_CORRECT. Otherwise it is BLOCKED_POLICY. Remove or update it by hand. /Applications must be a real folder, owned by root, with no ACL, and mode 0755, or 0775 with group admin.
